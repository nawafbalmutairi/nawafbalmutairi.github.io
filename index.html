i.The Brief

26 years of data,
one API outage.

Predict five water-quality parameters across 14 EA regions using 26 years of historical samples. Mid-build, the upstream Environment Agency API was deprecated (December 2025). Two choices: descope, or rebuild ingestion. I rebuilt it.

  • ~8.3M samples to ingest, partitioned by 14 EA areas × 26 years.
  • Five target parameters: Nitrate, BOD, Water Temp, Dissolved O₂, pH.
  • API deprecation cut the original Colab pipeline mid-flight.
  • Required a chronological train/test split — no peeking at the future.

ii.The Method

Treat the break
as system design.

Rebuilt ingestion in Colab using the new beta endpoint, automated 364 CSV downloads, batch-renamed with PowerShell, and verified with a script that caught a swapped year in the Thames data. Then a chronological train/test split (train 2000–2017, test 2018–2025) — not a random split, because real forecasting can't see the future.

  • Chronological split avoids data leakage common in time-series ML.
  • Verification script flagged a year-number mismatch before training.
  • Same preprocessing pipeline across all four models for fair comparison.
  • Ridge / Random Forest / MLP / XGBoost — linear to non-linear coverage.

i.The Brief

A supply chain
running on fragments.

NVIDIA dominates AI-grade GPUs, but its supply chain is not the strength its P&L is. The H100, H200, and B-series depend on a single advanced-node foundry (TSMC), a bottlenecked CoWoS packaging step, and a demand signal that swings violently with every generative-AI release cycle.

Backorders accumulate. Forecasts misfire. The problem is structural, not local — a single dashboard cannot just report KPIs; it has to make the system visible.

  • Long supplier lead times — advanced-node + CoWoS packaging constraints.
  • Demand volatility — hyperscalers and AI startups order in waves.
  • Backorder accumulation directly threatens revenue predictability.
  • Data fragmented across orders, supply, inventory, and logistics systems.

ii.System Dynamics

Why production
won't fix this alone.

SSM tells you what is connected. A causal loop diagram tells you how those connections feed on themselves. High demand → backorders → pressure → production push → strain → lead times → more backorders.

Two reinforcing loops, two balancing loops. The conclusion: NVIDIA cannot fix this with manufacturing expansion — it needs an information-driven intervention.

  • Demand Surge — demand ↑ → backorders ↑ → pressure ↑ → strain ↑.
  • Forecast Volatility — volatile orders → forecast error → unstable inventory.
  • Capacity Constraint — limits force forecast revisions.
  • Lead Time Adjustment — delays force re-planning.
Causal Loop Diagram · Reinforcing & balancing feedback
Six variables · two reinforcing loops (R), two balancing loops (B) · + same direction, − opposite.
R1 · Demand Surge — demand ↑ → backorders ↑ → pressure ↑ → strain ↑ (reinforcing)
R2 · Forecast Volatility — volatile orders → forecast error → unstable inventory (reinforcing)
B1 · Capacity Constraint — production limits → unmet demand → revised forecasts (balancing)
B2 · Lead Time Adjustment — long lead times → delayed shipments → re-planning (balancing)

Built four model configurations in Azure ML Designer to recognise human faces and classify into Male / Female: DenseNet and ResNet, each evaluated in both a training pipeline (Kaggle Gender_images, 100 photos) and a real-time inference pipeline (a custom dataset of 30 photos I curated myself).

i.The Brief

Two architectures,
one Azure pipeline.

Build ML models in Azure ML Designer to recognise human faces and classify them into Male / Female. Compare DenseNet (densely-connected CNN) against ResNet (residual-network CNN), then re-run both as real-time inference pipelines against a separate dataset.

  • Training set: gender_images — Kaggle, 100 photos (50 male, 50 female).
  • Inference set: Nawaf_data_inference — 30 photos (15 / 15), self-curated.
  • Identical preprocessing across both architectures — fair architectural comparison.
  • Four configurations evaluated end-to-end: DenseNet train, ResNet train, DenseNet inference, ResNet inference.

ii.The Method

Identical pipeline,
two architectures, two modes.

Every step of the pipeline was held constant across both architectures: the same Convert to Image Directory step, the same 70/30 splits, the same Init + Apply Image Transformation chain. The only difference was the model component — DenseNet or ResNet — feeding into Train PyTorch Model on GPU compute. That isolation lets the architecture be the variable, not the noise.

Then a second pipeline reuses each trained model in real-time inference against Nawaf_data_inference, a 30-photo set I curated myself. This tests generalisation: does the model recognise faces it has never seen?

  • Same preprocessing for both models — architectural comparison is fair.
  • Train PyTorch Model on GPU — recommended for image classification at this scale.
  • Score Image Model + Evaluate Model surface precision / recall / accuracy automatically.
  • Real-time inference tests generalisation on a held-out 30-photo set.
