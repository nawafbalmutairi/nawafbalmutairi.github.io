01

Machine Learning · Dissertation

Benchmarking four ML models on 8.3 million water-quality samples.

KV6013 · 2026 · Final-year project

UK Environment Agency dataset, 2000–2025, five water-quality parameters. Mid-project, the upstream API was deprecated — so I rebuilt ingestion in Colab, batch-renamed 364 CSVs across 14 regions, and ran a chronological train/test split to benchmark Ridge, Random Forest, MLP, and XGBoost. The break became a system-design problem.

i. The Brief

26 years of data, one API outage.

Predict five water-quality parameters across 14 EA regions using 26 years of historical samples. Mid-build, the upstream Environment Agency API was deprecated (December 2025). Two choices: descope, or rebuild ingestion. I rebuilt it.

  • ~8.3M samples to ingest, partitioned by 14 EA areas × 26 years.
  • Five target parameters: Nitrate, BOD, Water Temp, Dissolved O₂, pH.
  • API deprecation cut the original Colab pipeline mid-flight.
  • Required a chronological train/test split — no peeking at the future.

Fig. 02 — Data ingestion pipeline · rebuilt post-API outage

Six-stage flow from broken upstream source to fair model benchmark — the pipeline rebuilt after the December 2025 API deprecation.

  1. 01.EA APIUK Environment Agency endpoint, deprecated Dec 2025.✕ broken
  2. 02.Colab IngestAuto-download 364 monthly CSVs (26y × 14 regions) via new beta endpoint.⏵ python
  3. 03.PS RenamePowerShell batch rename — region prefix + year, 14 EA areas.⏵ shell
  4. 04.VerifyValidation script catches a year-number mismatch in Thames data.⏵ caught 1 bug
  5. 05.SplitChronological train/test split — train 2000–2017, test 2018–2025.⏵ 27M / 6M cumulative
  6. 06.BenchmarkRidge, RF, MLP, XGBoost — same preprocessing, fair comparison.★ XGBoost wins

ii. The Method

Treat the break as system design.

Rebuilt ingestion in Colab using the new beta endpoint, automated 364 CSV downloads, batch-renamed with PowerShell, and verified with a script that caught a swapped year in the Thames data. Then a chronological train/test split (train 2000–2017, test 2018–2025) — not a random split, because real forecasting can't see the future.

  • Chronological split avoids data leakage common in time-series ML.
  • Verification script flagged a year-number mismatch before training.
  • Same preprocessing pipeline across all four models for fair comparison.
  • Ridge / Random Forest / MLP / XGBoost — linear to non-linear coverage.

The Takeaway

"When an API breaks halfway through, you have two options: descope, or treat the break as system design. The second answer is almost always better."

NVIDIA AI-GPU supply chain dashboard.

2025 · Power BI · Word count 3,632

An integrated BI solution for one of the world's most volatile supply chains. Using Soft Systems Methodology, CATWOE, and the Balanced Scorecard, I structured NVIDIA's AI-GPU forecasting problem from rich picture to KPI to live dashboard.

i. The Brief

A supply chain running on fragments.

NVIDIA dominates AI-grade GPUs, but its supply chain is not the strength its P&L is. The H100, H200, and B-series depend on a single advanced-node foundry (TSMC), a bottlenecked CoWoS packaging step, and a demand signal that swings violently with every generative-AI release cycle. Backorders accumulate. Forecasts misfire. The problem is structural, not local — a single dashboard cannot just report KPIs; it has to make the system visible.

  • Long supplier lead times — advanced-node + CoWoS packaging constraints.
  • Demand volatility — hyperscalers and AI startups order in waves.
  • Backorder accumulation directly threatens revenue predictability.
  • Data fragmented across orders, supply, inventory, and logistics systems.

Fig. 02 — Rich picture · SSM ecosystem diagram

NVIDIA Operations & Planning at the centre; actors, flows, and external pressures around it.

  • Centre — NVIDIA Ops & Planning, the actor whose decisions we want the dashboard to support.
  • Upstream — TSMC (advanced foundry) & CoWoS packaging, capacity-constrained.
  • Downstream — cloud hyperscalers, enterprise, OEMs, logistics: demand & delivery.
  • Pressures — competitors, geopolitics & export controls, market expectations.
  • Driver — generative-AI demand, explosive and volatile.
  • Pain — backorders / unserved demand, the visible failure.

ii. System Dynamics

Why production won't fix this alone.

SSM tells you what is connected. A causal loop diagram tells you how those connections feed on themselves. High demand → backorders → pressure → production push → strain → lead times → more backorders. Two reinforcing loops, two balancing loops. The conclusion: NVIDIA cannot fix this with manufacturing expansion — it needs an information-driven intervention.

  • R1 · Demand Surge — demand ↑ → backorders ↑ → pressure ↑ → strain ↑ (reinforcing).
  • R2 · Forecast Volatility — volatile orders → forecast error → unstable inventory (reinforcing).
  • B1 · Capacity Constraint — production limits force forecast revisions: limits → unmet demand → revised forecasts (balancing).
  • B2 · Lead Time Adjustment — long lead times → delayed shipments → re-planning (balancing).

Fig. 03 — Causal loop diagram · reinforcing & balancing feedback: six variables, two reinforcing loops (R), two balancing loops (B). + same direction, − opposite.

iii. Strategy

From insight to scorecard.

CATWOE clarified ownership and worldview. The Balanced Scorecard translated insight into strategy: Learning & Growth capabilities feed Internal Processes, which improve Customer outcomes, which protect Financial performance. Every KPI on the dashboard now has a place in the strategy. Nothing reports for its own sake.

  1. 01 · Learning & GrowthBuild the capabilityBI & data analytics skills · forecasting expertise · system-dynamics thinking · tool fluency: Power BI, DAX.
  2. 02 · Internal ProcessesImprove the engineReduce forecast error (MAPE) · tighten supply planning · resolve CoWoS bottlenecks · balance capacity utilisation.
  3. 03 · CustomerEarn loyaltyShorter lead times · higher on-time delivery · fewer unserved orders · confidence in supply.
  4. 04 · FinancialProtect the resultPredictable revenue · lower cost of delays · minimise lost sales · stable margin profile.

Fig. 04 — Strategy map · Balanced Scorecard linking capabilities to outcomes. Capabilities at the bottom build through internal processes to customer outcomes, ending in financial result.

Deep Learning · Azure ML Designer

Gender classification on faces — DenseNet vs ResNet, four configurations.

2024 · Computer Vision · Azure ML · PyTorch

Built four model configurations in Azure ML Designer to recognise human faces and classify into Male / Female: DenseNet and ResNet, each evaluated in both a training pipeline (Kaggle Gender_images, 100 photos) and a real-time inference pipeline (a custom dataset of 30 photos I curated myself).

  • Azure ML Designer
  • PyTorch
  • DenseNet
  • ResNet
  • Computer Vision
  • GPU Training

Live architectures — dense connectivity vs residual shortcuts

Fig. 01 — Azure ML Designer pipeline · 2024

⏵ gender_images.pipeline

Five stages from raw images to evaluation. The same pipeline is run with DenseNet and ResNet; a second pipeline reuses the trained models for real-time inference on a custom dataset.

Training pipeline · 5 stages

  1. 01.Datasetgender_images — Kaggle, 100 photos (50M / 50F).⏵ 100 imgs
  2. 02.Convert & SplitConvert to Image Directory · split 70/30 train/test, then 70/30 train/val.⏵ azure

i. The Brief

Two architectures, one Azure pipeline.

Build ML models in Azure ML Designer to recognise human faces and classify them into Male / Female. Compare DenseNet (densely-connected CNN) against ResNet (residual-network CNN), then re-run both as real-time inference pipelines against a separate dataset.

  • Training set: gender_images — Kaggle, 100 photos (50 male, 50 female).
  • Inference set: Nawaf_data_inference — 30 photos (15 / 15), self-curated.
  • Identical preprocessing across both architectures — fair architectural comparison.
  • Four configurations evaluated end-to-end: DenseNet train, ResNet train, DenseNet inference, ResNet inference.

Fig. 02 — Real-time inference pipeline · reuses the trained model

Second pipeline — apply trained DenseNet / ResNet to Nawaf_data_inference (30 new photos).

  1. 01.New DatasetNawaf_data_inference — 30 photos.⏵ 30 imgs
  2. 02.Convert & TransformConvert to Image Directory + Apply Image Transformation.⏵ azure
  3. 03.Score (trained model)Score Image Model uses the previously trained DenseNet / ResNet weights.⏵ inference
  4. 04.EvaluatePrecision · recall · accuracy on the unseen 30-photo set.★ 86.67%

ii. The Method

Identical pipeline, two architectures, two modes.

Every step of the pipeline was held constant across both architectures: the same Convert to Image Directory step, the same 70/30 splits, the same Init + Apply Image Transformation chain. The only difference was the model component — DenseNet or ResNet — feeding into Train PyTorch Model on GPU compute. That isolation lets the architecture be the variable, not the noise.

Then a second pipeline reuses each trained model in real-time inference against Nawaf_data_inference, a 30-photo set I curated myself. This tests generalisation: does the model recognise faces it has never seen?

  • Same preprocessing for both models — architectural comparison is fair.
  • Train PyTorch Model on GPU — recommended for image classification at this scale.
  • Score Image Model + Evaluate Model surface precision / recall / accuracy automatically.
  • Real-time inference tests generalisation on a held-out 30-photo set.

DenseNet · real-time inference · 0.8667 — the winning configuration. The trained DenseNet model, applied to Nawaf_data_inference (30 unseen photos), beats every other run including its own training-set evaluation (0.80). Real-world generalisation is consistent across all three metrics — precision, recall, and accuracy all land at 0.8667, meaning errors are evenly distributed between male and female classes.

The Takeaway

"DenseNet's dense connectivity captured face features more effectively than ResNet's residual blocks on this dataset. The real test was generalisation — and the model that won on the training set kept winning on the held-out photos."
